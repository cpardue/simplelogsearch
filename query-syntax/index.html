Log Search Query Syntax: AND, OR, NOT, and Quoted Phrases

SimpleLogSearch speaks one small, predictable query language: three boolean operators — AND, OR and NOT — plus double-quoted phrases. That is the entire syntax. This reference documents every rule the parser implements, with concrete examples taken from a 24-line sample application log so you can see exactly which lines each query would return before you ever run it. If you only read one section, make it the worked precedence example below: it steps through the canonical multi-ID correlation query the way the engine itself evaluates it.

The basic idea: terms and phrases

Every query is built from two blocks. A term is a single token with no whitespace — error, MID, 192.168.1.1. A phrase is anything wrapped in double quotes, spaces included — "status=500", "MID 123456", "timeout after 30s". Both are tested against each line of the file as a case-insensitive substring: the engine asks one question per line — "does this exact sequence of characters appear anywhere here?" Grep-style. No word boundaries, no regular expressions, no wildcards, no field syntax.

A query is evaluated independently per line: a line either matches or it does not, and the result window shows only the matching lines while keeping each line's original number from the file. A hit on line 4,182 of your log is labeled 4,182 — jump straight back to your editor, SIEM or text tool.

The three operators

AND keeps lines matching every branch, OR keeps lines matching at least one branch, and NOT removes any line where its argument appears — anywhere on the line. Six examples against the 24-line sample log:

OperatorExample queryWhat it matches in the sample log
AND"status=500" AND paymentsLines carrying both the failed request and the payments dependency on the same line — the classic "what broke, and why" pair.
error AND timeoutAny line mentioning both words; order and distance between them do not matter.
OR"status=200" OR "status=500"Every healthy or failed request line: lines 6, 11 and 15.
"svc=api" OR "svc=db"All API-service and database-service lines — a broad first pass before narrowing.
NOTNOT "192.168.1.1"Every line that does not mention that IP at all — 17 of the 24 sample lines, and line 10 is excluded too, because its 192.168.1.10 still contains the quoted substring.
"svc=db" NOT vacuumDatabase lines minus the routine maintenance noise.

Operator tokens are matched as whole words in any casing — and, And and AND parse identically. That same rule is why a bare and can never be searched for literally (see mistake five below).

Precedence and parentheses

When a query mixes operators without parentheses, SimpleLogSearch binds them in a fixed order: NOT tightest, then AND, then OR. So a OR b AND c is evaluated as a OR (b AND c), never as (a OR b) AND c. Parentheses override precedence completely and are always legal — when a query gets long, adding them costs nothing and removes all doubt.

Here is the engine's canonical example, worked step by step against the 24-line sample log:

"MID 123456" and "MID 123654" not "192.168.1.1"

Step 1 — apply precedence. There are no parentheses. The not claims only its immediate argument, "192.168.1.1", and the and chain evaluates left to right, so the query is exactly equivalent to:

("MID 123456" AND "MID 123654") AND NOT "192.168.1.1"

Step 2 — the inner AND. A line must contain both correlation IDs. In the sample log exactly two lines qualify:

  • Line 7 — … WARN svc=api MID 123456 and MID 123654 correlated by trace=t-77
  • Line 20 — … ERROR svc=db MID 123456 MID 123654 replication lag 52s host=db-2 via 192.168.1.1

Step 3 — the NOT exclusion. NOT filters whole lines: any line containing 192.168.1.1 anywhere is dropped, even when that IP sits outside the matched phrases. Line 20 ends with via 192.168.1.1, so it is removed. The final result is a single line — line 7, the one place both IDs appear without the noisy address.

That last step is the one to internalize: an exclusion applies to the entire line, not just to what the AND matched. Appending not "noise" at the end of any query removes every line where "noise" appears — almost always the behaviour you want when correlating incidents.

Implicit AND

Two operands placed side by side are ANDed — the whitespace between them is itself the operator. That means unquoted MID 123456 is not one phrase; it is the term MID AND the term 123456, and it matches any line containing both substrings anywhere, in either order. The quoted form "MID 123456" requires the exact adjacent sequence instead. On the sample log both happen to return the same seven lines, but on a messier file they can diverge — so quote whenever you mean the literal sequence.

Case-insensitive matching — and one substring caveat

Every test is case-insensitive: mid 123456, MID 123456 and "Status=200" all match the exact-case spellings in the log, so you can type queries however you like. The other side of substring matching is a caveat worth knowing: because there are no word boundaries, "192.168.1.1" also matches a line that contains only 192.168.1.10 — sample log line 10, packet loss to 192.168.1.10 interface=eth0, is caught by it. The standard fix is to quote one extra character of context, usually a trailing space: "192.168.1.1 " matches only lines where the IP is followed by whitespace, which narrows the sample log to line 16 alone. The same trick disambiguates any prefix collision — "status=50" versus "status=500", a short hostname inside a long one, table prefixes.

Five common mistakes

  1. Missing quotes on a multi-word phrase. timeout after without quotes is two terms ANDed — it matches a line containing both words in either order, even far apart. Only "timeout after" demands the exact sequence.
  2. Believing operators must be typed in one case. They do not — and, And and AND (the same for OR and NOT) are matched as whole tokens in any casing and parse identically. A lowercase query behaves exactly like an uppercase one.
  3. Empty phrases. "" — two quotes with nothing between them — is a rejected query ("empty phrase"), not a zero-result search. Remove the empty pair; there is nothing for it to match.
  4. Dangling operators. Every NOT, AND and OR needs a search term on each side: "svc=api" AND, AND "svc=api" and OR OR are all rejected with an explicit "missing a search term" error. Count your operators against your terms before pressing Enter.
  5. Searching for the literal word "and" unquoted. A bare operator token is always an operator, never a literal — typing it inside a query changes the logic instead of searching for the word. Quote it: "and" matches the word itself (row 12 above).

That is the whole language: three operators, one quoting rule, one precedence chain.
